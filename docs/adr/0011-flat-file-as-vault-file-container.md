# Flat file as the vault file container

Supersedes ADR-0006. The vault file `secrets.vault` is now the raw encoded header followed by the encrypted body (`header ‖ body`), with no container around them. SQLite held these two blobs in a single row and ran no real query, and it was kept only because the ICS0027 requirements name prepared, parameterized statements as a defence against SQL injection. The instructor has approved dropping it: SQL was the course's example of that defence, not a rule that the app must use a database. Security of the application comes before the letter of the guidelines, and a smaller design is easier to secure and to defend in class. With a flat file, a vault file from an untrusted place (e.g. a restored backup) only ever meets one small, strict parser, `Header::decode`, instead of SQLite's C parser. There is no query language left to inject into, so injection is ruled out by design instead of being guarded against. The build becomes pure Rust and no longer needs a C compiler.

## Consequences

- The header's magic `SPMV` and format version are the only identification of a vault file; storage adds no version of its own. A file shorter than the header, or whose first 126 bytes don't decode, is not a vault. The body is everything after the header and is authenticated later, by crypto.
- A save writes the new vault to a `0600` temp file in the vault home, fsyncs it, renames it over `secrets.vault` and fsyncs the vault home, so a crash leaves either the old vault or the new one, never a mix. Once the rename is done the save has happened: a failed fsync of the vault home after it is logged, not reported as a failed save, or the session would undo a change that is on disk. A temp file left by a crash holds a whole sealed vault, so the next save removes it.
- Two sessions still can't overwrite each other. A save holds an exclusive lock on `secrets.lock`, an empty file in the vault home, while it checks that the stored header's revision is the one the new revision follows, and while it renames. `secrets.vault` itself can't be the lock, because the rename replaces it. The lock file is created on the first save (`0600`, symlinks refused), and a save that can't get it within 5 seconds fails. Loads and `init` take no lock: a rename and a hard link are atomic, so a reader sees the old file or the new one.
- Each save replaces the whole file, so the vault file never holds old ciphertext. The old file's disk blocks are freed but not zeroed and may still hold the previous ciphertext, including a header wrapped under a rotated master password. This is accepted, as SQLite's leftover rollback journal was before.
- A vault file over 64 MiB is refused before it is read; a real vault is a few KiB, and the limit only stops a planted file from exhausting memory.
- Locking uses `std::fs::File::try_lock`, so the minimum Rust version is 1.89.
